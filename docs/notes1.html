Centre For Sight: OptiFlow

Complete technical overview and transition guide for automated inventory allocation from the Dwarka warehouse to PAN India stores.

Client Context: Centre For Sight

Centre For Sight operates a geographically distributed network of optical stores across India. Their entire supply chain is anchored by a single, central warehouse located in Dwarka, New Delhi.

The Dwarka warehouse acts as a continuous supplier (it does not flag stockouts in this allocation model). The core logistical challenge is accurately calculating the specific Planogram deficits at each PAN India store and determining exactly which frames / sunglasses (or substitutes) need to be dispatched from Dwarka to fulfill those gaps.

The Pressing Issue

Manual Bottlenecks & Wasted Time

Currently at Centre For Sight, inventory replenishment is driven entirely by manual Excel spreadsheets. The central warehouse in Dwarka, New Delhi receives inventory (acting as a continuous supplier without stockouts), and merchandisers must export raw data, run complex VLOOKUPs to compare PAN India store stock against Planograms.

It takes a massive amount of time for the team to manually figure out which substitute frame / sunglass goes to which PAN India store when an exact SKU isn't available.

This manual process introduces significant operational bottlenecks. Across the network, this process requires over 191 manual events per month, wasting an estimated 12,600+ hours annually. Our immediate focus is to address this first.

Proposed Method

The Automated Solution

We are deploying a deterministic Logic Engine. The user simply uploads the raw PAN India store and Dwarka warehouse CSV data. The system automatically calculates Planogram deficits for each store and executes allocations.

Fully Automated 3-Step Substitutions: If an exact frame / sunglass is out of stock in the warehouse, the system automatically runs a heuristic search to find a similar item. If a similar item is not found, it picks a NEW item from the SAME BRAND. The engine allocates it immediately. No manager approval or manual click is required.

1. System Roles & Access Control (RBAC)

The platform restricts actions based on two distinct user tiers:

Basic User (Store Managers / Warehouse Staff)
  • Permissions: View-only access to dashboards, stock levels, and calculated metrics.
  • Outputs: Can filter and print physical Dispatch Orders and packing slips. Cannot modify data or upload files.
Admin (Corporate Merchandising / Corporate Team)
  • Permissions: Full read/write/execute control over the platform.
  • Actions: Uploads all CSV feeds, modifies data rows inline, adjusts heuristic search weights, and receives system health alerts.

2. Data Ingestion Architecture (The Inputs)

The system ingests data through three standardized CSV structures. The columns are fixed per file type, and only the row data changes dynamically.

  • Planogram Master Data: Serves as the stable source of truth. Admins have full control to add or delete rows (e.g., introducing a new brand like "Brand P" or removing a discontinued one).
  • Sales Data: Accepts historical data (the initial 6-month block). Every 7 days, Admins upload an incremental 7-day CSV. The system performs an Upsert based on the transaction log to append new sales tracking data without overwriting history.
  • Stock Data (Unified PAN India Store & Dwarka Warehouse Feed): A single, consolidated CSV that captures current stock levels across the entire network. The system differentiates locations based on the identifier in the store name column. Ingesting this file overwrites the previous snapshot to provide real-time visibility.

Inventory Tracking Mechanisms

1. Barcode: Used to track the physical order lifecycle. It is highly dynamic, often associated with order dates, and changes based on each specific order.

2. Item Code: A static, permanent identifier assigned to each SKU. This never changes and serves as the primary key for the heuristics engine to track and evaluate frames / sunglasses across the network.

3. Core Calculation & Heuristic Engine

When an Admin runs a cycle, the system executes three sequential algorithmic layers:

Layer A: The Deficit & Uniqueness Evaluator

1. Store Deficit Calculation: For every PAN India store, brand, and SKU, the engine calculates the fulfillment target:

Deficit = (Facing + Back stock) - Current Store SOH

2. The 85% Uniqueness Filter (Soft Warning): During validation, the system aggregates the metrics per brand per store:

Uniqueness Ratio = (Unique SKU Count for Brand) / (Total SOH Inventory for Brand)

Layer B: Waterfall Prioritization Logic

If total network demand outpaces the Dwarka warehouse supply batch, stock allocation drops down a strict multi-tier priority cascade:

  • Store Grade Tiering: Allocate completely to Grade A stores first → then Grade B → then Grade C.
  • Internal Grade List: Within Grade A (or B/C), the engine allocates inventory based on a secondary, client-provided internal ranking array.

Layer C: Auto-Substitution Match Cascade

When a specific SKU deficit is identified for a store, the engine executes a strict 3-tier substitution hierarchy from the Dwarka warehouse supply:

[SKU Deficit Identified for Store] │ ├──► 1. Exact Match in WH? ──► YES ──► Auto-Allocate SKU │ └──► NO ──► 2. Similar Item Heuristic │ (Brand ──► Frame vs Sunglass ──► Price ──► Attributes) │ ├──► Match Found? ──► YES ──► Auto-Allocate Substitute │ └──► NO ──► 3. New Item Assignment └──► Must be SAME BRAND ──► Auto-Allocate New Item

Store Display Constraint Rule: During allocations, the engine enforces a strict constraint: Maximum of 2 colors of the same type of frame / sunglass per store. If a 3rd color is allocated, the system allows it but it is marked in RED on the output reports to warn the user.

4. Reporting & Output Generation

Once the engine finishes calculations, it outputs clean, isolated datasets ready for physical action:

  • Recommended Distribution Report: A clean master grid showing what SKU (or chosen heuristic match) is assigned to go where.
  • Dynamic UI Filters & Printing: Users can filter and print out Dispatch Orders dynamically based on Brand, Store, or a combined All view.
  • Print-Optimized Dispatch Orders: Single-click formatting for warehouse staff to print physical picking lists.

5. Intelligent Analytics Layer (Future Capability)

The underlying database architecture will handle data collection to support these automated features:

  • Cold-Start Engine (New Brands): When a brand-new brand is added to a store layout, the engine bypasses the 6-month baseline and calculates its performance velocity solely on its past 7 days of incremental sales.
  • Dynamic Demand Adjustments: A script that monitors rolling 30-day barcode velocity. If a brand's sales slide consistently, the engine recommends lowering that store's target allocation by 10% to 20%.
  • Cross-Pollination Recommendation: If a certain price point for frames / sunglasses is booming in a store, the system scans the warehouse stock for idle inventory from other brands matching that exact price bracket.
